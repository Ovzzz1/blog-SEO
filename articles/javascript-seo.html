01

The Core Problem

Traditional websites deliver HTML files verbatim. What the server sends is what the browser — and the crawler — sees. Simple, predictable, immediately readable.

JavaScript frameworks broke that contract.

When a site is built as a pure Single Page Application (SPA), the server sends this:

<!doctype html>
<html>
  <head><title>App</title></head>
  <body>
    <div id="root"></div>
    <script src="/static/js/main.bundle.js"></script>
  </body>
</html>

That's it. There is no content. The browser downloads the JavaScript bundle, executes it, fetches data from APIs, builds the DOM in memory, and finally injects visible content into #root. Until that chain completes, the page is a blank shell.

For SEO, this is a problem at multiple levels:

  • Crawlers that don't execute JS see nothing
  • Even Googlebot, which does execute JS, puts these pages in a rendering queue — introducing delays
  • Social-media unfurlers (Twitter, LinkedIn, Facebook) don't run JS — so every page shows the same default preview
  • AI crawlers (GPTBot, ClaudeBot, PerplexityBot) fetch JS files but do not execute them — your content is invisible to them
Simplified analogy

A static HTML site is like a printed menu on a restaurant table — anyone can read it immediately. A JS-only SPA is a menu that only appears after you scan a QR code, wait for an app to load, log in, and grant location permissions. Most impatient guests (crawlers) give up.

Why developers still use frameworks: speed of development, rich interactivity, component reuse, shared logic between web and mobile. The problem isn't the frameworks themselves — it's deploying them in Client-Side Rendering mode for content that needs to be indexed. Meta-frameworks (Next.js, Nuxt, SvelteKit, Astro) exist precisely to solve this.

02

How the Browser and Googlebot Actually Read a Page

What HTML, CSS, and JavaScript each do

  • HTML: Declarative structure. Defines what exists on the page — headings, paragraphs, links, images, semantic elements. This is what crawlers fundamentally rely on. Strong semantic HTML (proper <h1>–<h6>, <article>, <nav>, <main>, <footer>) directly improves Google's and LLMs' ability to understand content hierarchy.
  • CSS: Presentation. Defines how things look. Doesn't affect crawling but does affect Core Web Vitals — specifically CLS if fonts load without size reservations, and LCP if critical styles are blocked.
  • JavaScript: Behaviour and dynamism. Manipulates the DOM after the fact. This is what introduces complexity for crawlers.

How a browser parses a page

  1. Receives the raw HTML from the server
  2. Parses it top-to-bottom, building the DOM tree
  3. When it encounters a <link rel="stylesheet">, it fetches CSS and builds the CSSOM
  4. When it encounters a <script> without defer or async, it stops parsing until the JS downloads and executes (render-blocking)
  5. Combines DOM + CSSOM into the Render Tree
  6. Layout phase: computes positions and sizes
  7. Paint phase: draws pixels

JavaScript's single-threaded event loop means that heavy JS execution monopolises the only thread that can also paint and respond to user input — which is why JS-heavy pages score poorly on INP and block the rendering pipeline.

How Googlebot processes a page

Google's pipeline has three distinct stages:

URL discovered → Crawl (fetch raw HTML) → Render Queue → WRS Render → Index

Stage 1 — Crawl: Googlebot fetches the raw HTTP response. It reads whatever HTML is in that response immediately. Any links in the static HTML are discovered now.

Stage 2 — Render Queue: If JS is needed to reveal content, the URL goes into a queue. This queue is resource-constrained — pages can wait from seconds to weeks depending on the site's authority, crawl budget, and server performance.

Stage 3 — WRS Render: Google's Web Rendering Service uses a headless Chromium instance (now evergreen — tracking the latest stable Chrome release since May 2019). It executes JavaScript, fetches API data, builds the full DOM, and extracts content and links.

Critical constraints of the WRS:

  • Stateless — no cookies, no localStorage, no session state persists between pages
  • Does not interact with the page (no clicks, no scroll, no form submission, no cookie-banner dismissal)
  • Has a 2 MB resource budget per page — heavy bundles may not fully execute
  • Has a ~5-second rendering timeout on average, though queuing can extend total delay significantly
  • Content revealed only through user interaction (click, hover, scroll) is invisible
2024 Study Finding

A 2024 study by Vercel and MERJ (analyzing 100,000+ Googlebot fetches) found that Google now renders virtually all pages returning a 200 status, including complex SPAs. However: server-rendered pages have an advantage because they skip the render queue entirely for content discovery.

03

Rendering Modes — The Decision That Changes Everything

The rendering mode determines what content is in the HTML when a crawler first receives it — which determines everything else.

Client-Side Rendering (CSR)

  • What it is: The server sends an empty HTML shell. All content is built by JavaScript in the browser.
  • What Googlebot sees on first fetch: An empty <div id="root">. No content, no links.
  • When it gets indexed: Only after the render queue processes the page — which could be immediate or days later.
  • Use case: Authenticated dashboards, admin panels, content behind a login wall that doesn't need SEO.
  • Never use for: Any page that needs to rank organically or be shared on social media.
Analogy

CSR is a restaurant where they bring you an empty plate and make you go to the kitchen yourself to fill it. Google will eventually visit the kitchen too — but it might take a while, and it won't always find everything.

Server-Side Rendering (SSR)

  • What it is: On every request, the server runs the framework code, fetches data, produces a fully-populated HTML document, and sends it.
  • What Googlebot sees: Complete HTML with all content, metadata, and links. No rendering queue needed.
  • When it gets indexed: Immediately on first crawl.
  • Performance trade-off: Higher TTFB (server must do work per request). Requires a running server — not a static CDN.
  • Use case: Dynamic content that changes frequently — e-commerce with live stock, news articles, search results.
Analogy

SSR is a restaurant where the chef cooks each dish fresh to order. The food (HTML) arrives ready to eat, but you wait a few minutes.

Static Site Generation (SSG)

  • What it is: Pages are pre-rendered at build time into HTML files. These files are deployed to a CDN and served instantly.
  • What Googlebot sees: Perfect, instant HTML. Best possible TTFB.
  • Trade-off: Content is frozen until the next build. Large sites (thousands of pages) can have build times of hours.
  • Use case: Marketing pages, blog posts, documentation, anything that doesn't change per-request.
Analogy

SSG is a printed menu. Fastest for the customer (crawler), but requires reprinting whenever the menu changes.

Incremental Static Regeneration (ISR) — Next.js specific

  • What it is: Pages start as SSG, but can be automatically rebuilt in the background at a specified interval (revalidate: 300 = rebuild every 5 minutes) or on-demand.
  • The mechanism: First request gets the cached static page. In the background, Next.js silently rebuilds a fresh version. Next visitor gets the fresh version ("stale-while-revalidate" pattern).
  • Use case: Large product catalogues where content updates periodically. E-commerce pricing, inventory, category pages.
  • Watch out for: Brief windows where the ISR page shows stale data (e.g., listing shows "in stock" while the ISR product page hasn't refreshed yet).

Hybrid Rendering

Modern meta-frameworks let you choose rendering mode per route. A single Next.js codebase can:

  • SSG the /blog/* routes (static articles)
  • ISR the /products/* routes (catalogue updated daily)
  • SSR the /search route (real-time results)
  • CSR the /dashboard/* routes (authenticated, no SEO needed)

This is the architecture you want for most professional sites.

Streaming SSR (Next.js App Router + React Suspense)

Instead of waiting for the entire page to render before sending HTML, the server streams HTML in chunks as components finish rendering. The browser receives the header and navigation immediately, then the main content streams in, then the comments or reviews.

SEO implication: The critical content (heading, body, metadata) is in the first chunk and arrives immediately. Even on slow data-fetching pages, Googlebot sees the key content fast.

Islands Architecture (Astro)

A fundamentally different approach: the server renders the entire page as static HTML. Only specific interactive widgets ("islands") are hydrated with JavaScript. The rest of the page ships zero JS.

SEO implication: Near-perfect Core Web Vitals. Immediate full HTML. Best for content-heavy sites where most pages don't need complex interactivity.

04

Next.js Deep Dive

What Next.js is

Next.js is a React meta-framework created by Vercel. It takes React (which is just a UI library — no router, no SSR, no data fetching conventions) and adds everything you need for a production website: routing, SSR/SSG/ISR, image optimization, font optimization, metadata management, API routes, middleware.

Major Next.js sites: TikTok, Notion, The Washington Post, Target, Nike, OpenAI, Twitch, Hulu, Deliveroo, Audible, Spotify.

Pages Router vs. App Router

Next.js has two parallel routing systems currently coexisting:

  • Pages Router (original, stable) — files in /pages/ become routes. getStaticProps → SSG, getServerSideProps → SSR. Metadata via next/head. Well-documented, mature ecosystem.
  • App Router (introduced Next.js 13, default since Next.js 14) — files in /app/; route = folder with page.tsx. Server Components by default. New Metadata API. Streaming SSR with React Suspense. Better SEO defaults, steeper learning curve.

For SEO work, you need to know which one the site uses — the audit approach differs significantly.

React Server Components (RSC) — Why They Matter for SEO

In the App Router, every component is a Server Component by default. Server Components render exclusively on the server, never ship their JavaScript to the browser, and their content is always in the initial HTML — no rendering queue issue.

Client Components (marked with "use client" at the top) hydrate in the browser like traditional React.

Common mistake

Wrapping entire page components in "use client" just to use one interactive element. This pushes all content into the client bundle, breaking SSR for that page. Fix: keep the page as a Server Component and isolate the interactive widget into a small Client Component.

The Metadata API — Critical for SEO

Pages Router (next/head):

import Head from 'next/head'

export default function ProductPage({ product }) {
  return (
    <>
      <Head>
        <title>{product.name} | Your Store</title>
        <meta name="description" content={product.description} />
        <link rel="canonical" href={`https://example.com/products/${product.slug}`} />
      </Head>
      {/* page content */}
    </>
  )
}
Warning

If a page is CSR and uses next/head inside a useEffect, the metadata won't be in the initial HTML — invisible to social-media crawlers.

App Router (Metadata API) — the correct, guaranteed approach:

// Static metadata
export const metadata = {
  title: 'About Us | Your Brand',
  description: 'Learn about our company.',
  alternates: { canonical: 'https://example.com/about' },
}

// Dynamic metadata — runs on server before page renders
export async function generateMetadata({ params }) {
  const product = await fetchProduct(params.slug)
  return {
    title: `${product.name} | Your Store`,
    description: product.description,
    openGraph: {
      title: product.name,
      images: [product.coverImage],
    },
    alternates: {
      canonical: `https://example.com/products/${product.slug}`,
    },
  }
}

generateMetadata runs on the server before the page renders. The resulting tags are guaranteed to be in the initial HTML — even for dynamic, database-driven pages.

Title templates — avoid repetitive site-name suffixes:

// In root layout (app/layout.tsx)
export const metadata = {
  title: {
    template: '%s | Your Brand',
    default:  'Your Brand',
  },
}

// In any child page — only define the specific subject
export const metadata = {
  title: 'Product Name', // renders as "Product Name | Your Brand"
}

metadataBase — critical for canonical URL resolution:

// In your root layout
export const metadata = {
  metadataBase: new URL('https://example.com'),
}
// Without this, relative URLs in metadata are left as-is.
// With it, /products/slug resolves to https://example.com/products/slug
// Prevents staging domains bleeding into production canonical tags.

Structured Data (JSON-LD) in Next.js

The correct pattern — inline in a Server Component:

// app/products/[slug]/page.tsx (Server Component)
export default async function ProductPage({ params }) {
  const product = await fetchProduct(params.slug)

  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'Product',
    name: product.name,
    description: product.description,
    image: product.images,
    offers: {
      '@type': 'Offer',
      price: product.price,
      priceCurrency: 'EUR',
    },
  }

  return (
    <>
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{
          __html: JSON.stringify(jsonLd).replace(/</g, '\\u003c'),
        }}
      />
      {/* page content */}
    </>
  )
}

The .replace(/</g, '\\u003c') is an XSS-prevention measure — never skip it. Because this is a Server Component, the JSON-LD is in the initial HTML. Google doesn't need to render JS to find it.

The broken pattern — injecting JSON-LD via useEffect:

// ❌ BROKEN for SEO — only fires after hydration
useEffect(() => {
  const script = document.createElement('script')
  script.type = 'application/ld+json'
  script.text = JSON.stringify(jsonLd)
  document.head.appendChild(script)
}, [])

Sitemap and robots.ts in Next.js

Dynamic sitemap (App Router):

// app/sitemap.ts
import type { MetadataRoute } from 'next'

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const products = await fetchAllProducts()
  return [
    { url: 'https://example.com', lastModified: new Date() },
    ...products.map(p => ({
      url:             `https://example.com/products/${p.slug}`,
      lastModified:    new Date(p.updatedAt),
      changeFrequency: 'weekly',
      priority:        0.8,
    })),
  ]
}

Dynamic robots.ts:

// app/robots.ts
import type { MetadataRoute } from 'next'

export default function robots(): MetadataRoute.Robots {
  return {
    rules: [
      { userAgent: '*', allow: '/', disallow: ['/admin/', '/private/'] },
      { userAgent: ['GPTBot', 'ClaudeBot'], disallow: '/' }, // optional AI blocking
    ],
    sitemap: 'https://example.com/sitemap.xml',
  }
}

next/image — Why It Matters for SEO

Using a regular <img> tag is a CWV risk. next/image requires width and height (reserves space before the image loads, eliminating image-related CLS), automatically serves WebP/AVIF, and lazy-loads off-screen images by default.

// LCP image — add priority to preload it
<Image src={hero} alt="Product hero" width={1200} height={600} priority />

// All other images — lazy by default
<Image src={product.thumbnail} alt={product.name} width={400} height={400} />

next/font — Eliminating Text-Based CLS

Font swapping is a major CLS source. next/font self-hosts Google Fonts at build time and uses CSS size-adjust to make the fallback font geometrically match the custom font — no visible shift when it loads.

import { Inter } from 'next/font/google'
const inter = Inter({ subsets: ['latin'], display: 'swap' })

// In your root layout:
<html className={inter.className}>

next/link — The SEO-Safe Way to Navigate

// ✅ Correct — renders an <a href> in the DOM, crawlable
<Link href="/products/slug">View Product</Link>

// ❌ Wrong — invisible to crawlers
<button onClick={() => router.push('/products/slug')}>View Product</button>
<div onClick={() => router.push('/products/slug')}>View Product</div>
Prefetch trap

On pages with hundreds of links (mega-menus, large catalogues), viewport-based prefetching fires dozens of background requests simultaneously — exhausting server resources and generating gigabytes of bandwidth waste. Fix: <Link href="/..." prefetch={false}> on dense link clusters, or implement hover-based prefetch only.

  • Eliminates hydration entirely via "resumability": the server serialises the full application state into the HTML. The browser simply continues from where the server left off — zero JS re-execution needed
  • JS only downloads on-demand as the user actually interacts with specific elements
  • Near-instant TTI regardless of application complexity
  • Still a smaller ecosystem — less production case study evidence than Next.js
06

The Full Map of JS SEO Failure Modes

6.1 — JS-Only Internal Links: The Invisible Architecture Problem

This is the most common and most devastating JS SEO mistake. Navigation implemented with onClick handlers, router.push(), or <button> elements instead of <a href>.

Why it matters: Googlebot does not click buttons. The crawl graph is built from <a href> discovery. If your main navigation, category links, and product links are all inside JS event handlers, Googlebot sees your site as a flat collection of orphan pages — no hierarchy, no link equity flow, no discovery of deep URLs.

// ❌ Invisible to crawlers
<div onClick={() => navigate('/category/shoes')}>Shoes</div>

// ✅ Crawlable
<Link href="/category/shoes">Shoes</Link>
<a href="/category/shoes">Shoes</a>

Screaming Frog check: Run a crawl with JS rendering disabled ("Text Only" mode). Any link that disappears compared to a JS-enabled crawl is a JS-only link.

6.2 — Content Not in Initial HTML

Symptoms: View source shows empty <div>. URL Inspection in GSC shows content, but indexing is delayed or unreliable.

Common causes: Pure CSR — the entire page relies on client JS. SSR set up incorrectly — getServerSideProps or getStaticProps not actually fetching data before render. Content inside useEffect — runs only after hydration, never in SSR.

Test: Open the page, then Ctrl+U (View Source). If your content isn't there, it's not in the initial HTML.

6.3 — JS-Managed Metadata

What goes wrong: <title>, <meta name="description">, canonical tags, Open Graph tags written by JS after page load.

Consequences: Social-media previews use the static HTML — usually a generic default. Google's WRS will eventually see the dynamic metadata, but there's a rendering lag. AI crawlers will not see it.

Fix for App Router: Use the Metadata API (metadata export or generateMetadata). Tags are guaranteed in the initial HTML. Fix for Pages Router: Use next/head inside getServerSideProps or getStaticProps — not inside useEffect.

6.4 — Soft 404s from Hydration Failures

A Soft 404 occurs when the server returns HTTP 200, but Google decides the page has no content and removes it from the index.

How it happens in Next.js: Server renders correct HTML → JS bundle reaches the browser → an error occurs during hydration → React's error boundary unmounts the DOM → Googlebot's WRS, rendering after the fact, sees the blank/error screen → Google classifies it as Soft 404.

Also happens when: An ISR page revalidates but the data fetch fails, so Next.js falls back to the stale version — which may itself be broken.

Detection: GSC → Coverage → "Soft 404" tab. Cross-reference with your JS error monitoring (Sentry, Datadog) for hydration-phase exceptions.

Fix: Implement proper error handling in data fetching. Use notFound() in Next.js App Router to return a real 404 when data isn't found (rather than rendering an empty component).

6.5 — Crawl Budget Drain from Heavy JS

Googlebot allocates finite crawl resources per domain. Rendering JS costs vastly more than parsing static HTML. A site with heavy bundles, slow server responses, or 5xx errors gets throttled.

What gets wasted: rendering 500KB JS bundles on top-level pages, following prefetch requests from next/link, crawling faceted navigation URLs, recrawling JS files every visit.

The signal: In GSC → Settings → Crawl Stats → by file type. If 70–80% of Googlebot's requests are going to .js files, you have a budget problem.

6.6 — Faceted Navigation & Index Bloat

E-commerce JS sites frequently generate millions of indexable URLs from filter combinations:

/shoes?color=black&size=42&brand=nike&material=leather&sort=price_asc

With JS routing, creating a new URL for every filter state is trivial — and by default, all of these are indexable. This creates duplicate content, crawl budget waste, and keyword cannibalization.

Solution architecture:

  • Keep low-value filter combinations client-only (update UI state without changing the URL)
  • For combinations that do get URLs, add <link rel="canonical"> pointing to the base category
  • Add robots.txt disallow for complex parameter strings

6.7 — Rendering-Only Content: Interaction Traps

Google does not interact with pages. Content that requires clicking a tab, hovering to show a dropdown, scrolling to trigger lazy loading, or clicking "Load More" is invisible to Googlebot.

Common examples: product specs inside a tabbed UI where only the first tab's content is in the initial DOM, FAQ sections where answers are hidden behind a JS accordion, infinite scroll without paginated HTML fallback.

Fix: Ensure all critical content is in the DOM on initial render, even if visually hidden. For tabs, render all tab content in HTML and use CSS to hide inactive tabs. For accordions, render all answers in HTML. For infinite scroll, include a standard ?page=2 pagination link with a real href.

6.8 — Hreflang Failures in JS Frameworks

Nuxt i18n bug (#2764): Canonical and hreflang URLs are URL-encoded — slashes become %2F. Google sees https://example.com/fr%2Fproducts instead of https://example.com/fr/products. This breaks the entire hreflang implementation.

Common hreflang mistakes in any JS framework:

  • Using relative URLs instead of absolute — Google requires absolute URLs with https://domain.com/
  • Wrong ISO language codes: uk is Ukrainian, not United Kingdom (use en-GB)
  • Hreflang managed by JS that fires after page load — social crawlers won't see it
  • Missing x-default hreflang

Detection: Compare raw HTML (View Source) hreflang tags with the rendered hreflang tags (DevTools Elements panel). If they differ, your hreflang is JS-generated and unreliable.

6.9 — The Prefetch Bandwidth Trap

By default, <Link> prefetches the destination page's data when the link enters the viewport. On a homepage with 200 links, loading the page triggers 200 background data requests.

Real-world impact: gigabytes of monthly bandwidth consumed by phantom prefetch requests. On high-traffic pages, these simultaneous requests function as a self-inflicted DDoS — backend slowdown → higher TTFB → Googlebot throttles crawl rate → crawl budget depletes.

// Disable prefetch on dense link clusters
<Link href="/product/123" prefetch={false}>Product Name</Link>

// Or hover-based prefetch only
const router = useRouter()
<Link
  href="/product/123"
  onMouseEnter={() => router.prefetch('/product/123')}
  prefetch={false}
>
  Product Name
</Link>

Case Studies — Real Problems, Real Solutions

Case 1 CSR React → Next.js SSG
Notion: Marketing Site Rebuild

Problem: Notion's marketing site was fully client-side rendered. Lighthouse ~50/100, unreliable Google crawling, 9MB+ of JS per page (mostly app code irrelevant to marketing), loading spinners on every page before content appeared.

Root cause: Marketing pages built the same way as the application — CSR, relying on runtime API calls and the full app JS bundle.

Solution: Complete rebuild of 109 React components in Next.js with SSG. Content fetched from Contentful at build time, not runtime. Separate marketing component library.

Lighthouse 50 → 97/100 · JS payload 9.1 MB → 847 KB (−91%) · Total page weight −75% · Loading spinners eliminated
Case 2 React SPA
LoveLove.pl — 800 Pages, Zero Indexed at Launch

Problem: Polish marketplace launched with 800 pages. After weeks, fewer than 10 were indexed. Social media previews broken across all pages.

Root cause: Pure client-side rendering. The HTML Google received was <div id="root"></div> for every URL.

Solution: Implemented Prerender.io behind AWS CloudFront. Bot user-agents receive pre-rendered static HTML; users continue getting the SPA experience.

Note: Dynamic rendering (Prerender.io approach) is Google-permitted but described as a workaround. For new sites, SSR/SSG is the durable solution.

800+ pages indexed within days · Social previews fixed immediately · Zero weeks of SSR refactoring needed
Case 3 Create React App + HashRouter → Next.js
B2B SaaS Docs — 12 of 340 Pages Indexed After 6 Months

Problem: After 6 months of operation, only 12 of 340 documentation pages appeared in Google's index. Organic traffic near zero.

Root cause (cascade):

  • HashRouter generates URLs like example.com/#/docs/setup — Google ignores the fragment, treats the entire site as one URL
  • Navigation implemented with <div onClick> instead of <a href> — links invisible to crawlers
  • Metadata hardcoded in index.html — every page had identical title and description
  • All content rendered client-side only

Solution (8 weeks): Migrated to Next.js with file-based routing (real History API URLs). Replaced all div-based navigation with <Link> components. Connected documentation to CMS with getStaticProps. Deployed generateStaticParams for all 340 pages.

Indexed pages 12 → 327 (96% of total) · Organic traffic +412% · Documentation ranking for long-tail queries within 6 weeks
Case 4 Next.js Pages Router → App Router
Hardcover — 20× Search Traffic in 4 Months

Problem: Book-discovery site with weak organic visibility. Large client-side bundle, poor Lighthouse scores, slow TTI.

Root cause: Initial implementation leaned heavily on CSR; "use client" overused at the page level, pushing book content into client bundles.

Solution: Migrated to App Router. All book content, descriptions, and metadata moved to Server Components. generateMetadata for dynamic SEO tags. Code-splitting for interactive elements.

Search traffic ×20 in 4 months
Case 5 Custom SSR React → Next.js
AutoZone — 820KB Monolithic Bundle, Rankings Collapsed

Problem: AutoZone (7,000+ stores) launched a custom SSR architecture that generated an 820KB monolithic JavaScript bundle. Mobile PageSpeed scores collapsed. Google rankings dropped from position 3 to position 9 for critical revenue keywords.

Root cause: Custom SSR without code splitting, tree shaking, or route-level optimization. The entire application JS shipped on every page.

Solution: 2-week sprint migrating to Next.js. Native code splitting eliminated 260KB of blocking JS from the initial payload. Hydration optimized per route.

Lost rankings fully recovered · AutoZone reclaimed #1 position for target keywords
Case 6 Unknown JS framework
IFTTT — JS Routing Destroys Internal Linking

Problem: IFTTT stagnated in search visibility after a frontend framework adoption. Organic traffic plateaued.

Root cause: The redesign replaced all HTML <a href> navigation with JavaScript-rendered links. Screaming Frog and Googlebot could not discover any internal links from the raw HTML. The site appeared as a flat, disconnected collection of pages with no hierarchy.

Solution: Refactored all structural navigation to use standard <a href> attributes. JS routing kept for the interactive app experience, but all SEO-critical navigation paths rendered as static HTML links.

Internal linking restored → crawl efficiency recovered → +33% organic traffic growth
Case 7 Legacy CMS → React SPA (CSR)
E-commerce — Complete Traffic Collapse After Migration

Problem: Domain migration coincided with a platform shift to pure CSR. Traffic entered a terminal multi-month decline to near zero.

Root cause (forensic audit findings):

  • Pure CSR — Google couldn't index product inventory
  • No canonical tags → index bloat from duplicate URLs
  • Staging environment noindex tags left in production codebase
  • No redirect map from legacy URLs → lost all link equity

Solution: Complete refactor to Next.js SSR. 301 redirects from all legacy URLs. Programmatic metadata across category pages. Canonical tags on all product URLs.

Full organic traffic restoration and revenue stabilisation
Case 8 SvelteKit adapter-static (SPA mode)
gloverab.com — Wrong URLs in Google from SPA Mode

Problem: Product pages for manufacturers (e.g., /general-electric-products) were indexed, but with the broken fallback URL (/0-products) appearing in search results.

Root cause: In SPA mode, manufacturerSlug was null during server rendering (no SSR). The fallback rendered /0-products. Google indexed the fallback state, not the real URL.

Solution: Reversed the SPA mode mandate. Reinstated adapter-node with SSR. Database queries now execute on the server, injecting manufacturer data into the initial HTML before transmission.

Correct product URLs indexed · Real manufacturer pages appearing in search results
Case 9 Next.js SSR (per-request)
Healthcare Marketplace — INP Failures Suppressing Rankings

Problem: Mobile INP consistently >300ms (failing threshold). Despite correct SSR setup, search visibility suppressed.

Root cause: Every page view triggered real-time backend server requests, creating SSR render delays that blocked the client's main thread during hydration, causing interaction lag.

Solution: Shifted from per-request SSR to SSG for 20,000+ pages. All interactive elements refactored to Client Components with pre-fetched data.

INP 300ms → 60–100ms (Failing → Good) · Sustained organic ranking uplift within days of deployment
Case 10 Next.js SSR vs traditional server-side HTML
Nike vs New Balance — The 9MB Hydration Bundle Problem

Problem: Nike's SSR-rendered pages shipped a 9MB hydration bundle to the client. Technically SSR, so the initial HTML was correct — but the JS required to make the page interactive was enormous. AI crawlers and non-Google bots that timed out while hydrating saw an effectively broken page. New Balance's lean server-side HTML with minimal JS was parsed instantly.

Lesson: SSR doesn't immunise you from JS bloat. A 9MB hydration bundle creates a Time-to-Interactive delay that affects both users and crawlers that aren't as patient as Googlebot's WRS. Code-split aggressively. Monitor JS payload per route.

New Balance's minimal JS approach outperformed Nike's SSR for non-Google crawlers
Case 11 Unspecified JS framework
Lifestyle E-commerce — 45% Traffic Decline from Internal Linking Collapse

Problem: 45% organic traffic decline over six months from internal linking collapse and rendering issues. Internal dev team had prioritised feature velocity over SEO.

Root cause: Critical on-page navigation rendered exclusively via client-side JS. CMS migration misconfigured canonical tags. Schema markup inconsistent across templates.

Solution: Enforced HTML-based internal linking throughout. Standardised schema templates. Canonical tags corrected globally.

Crawl efficiency restored · Full search visibility recovered
Case 12 Nuxt + @nuxtjs/i18n
Nuxt i18n Hreflang Bug in Production (Issues #2764 & #3460)

Issue: Multiple production Nuxt sites discovered that @nuxtjs/i18n was URL-encoding hreflang href attributes — https://example.com/fr/produits becoming https://example.com/fr%2Fproduits. Google couldn't match these to real URLs. A secondary issue (#3460) generated hreflang tags for locales that had seo: false configured.

Impact: Indexing problems, content-duplication concerns, Lighthouse SEO score regression, entire hreflang implementation non-functional.

Fixes used in production:

  1. Pin to a known-good version of @nuxtjs/i18n where the bug is fixed
  2. Replace the built-in hreflang generation with a custom composable using useHead and explicit absolute URLs
  3. Validate all hreflang tags by checking raw HTML (View Source), not the rendered DOM
Detection: View Source → check for %2F in hreflang href attributes

Auditing a JS Framework Site — Step-by-Step Playbook

Step 1
Identify the framework and rendering mode
Signal in sourceFramework
<div id="__next"> + <script id="__NEXT_DATA__">Next.js (Pages Router)
self.__next_f.push( in sourceNext.js (App Router)
<div id="__nuxt"> + window.__NUXT__Nuxt
<div id="app"> + data-server-rendered="true"Vue SSR / Nuxt 2
astro-island elements in DOMAstro
<sveltekit-data>SvelteKit
ng-version attribute on root elementAngular

Determine rendering mode: View Source (Ctrl+U) — is your content in the raw HTML? Yes = SSR/SSG. No = CSR or broken SSR. Check HTTP headers: x-powered-by: Next.js, x-vercel-cache: HIT (ISR/SSG cache hit).

Step 2
Compare raw HTML vs rendered DOM — the core audit step

Tool: Screaming Frog → Configuration → Spider → Rendering → select "JavaScript"

Run two crawls: (1) Rendering: "Text Only" — disabled JS, what crawlers see in their first pass. (2) Rendering: "JavaScript" — what Googlebot sees after rendering.

  • Links present in crawl 2 but absent in crawl 1: JS-only links — critical problem
  • Metadata present in crawl 2 but absent in crawl 1: JS-managed metadata — at risk

Also use: GSC → URL Inspection → "Test Live URL" → "View Crawled Page". The HTML tab shows what Google's WRS saw. The Screenshot tab shows what the page looked like visually to Google. If the screenshot shows an error screen or blank content, you have a hydration/rendering problem.

Step 3
Verify metadata in raw HTML

For every critical page template (homepage, category, product, blog post), run View Source and search for these — all must be present in raw HTML:

<title>
<meta name="description"
<link rel="canonical"
<meta property="og:title"
<script type="application/ld+json"

If any are absent or show generic/default values, that template has a metadata problem.

Step 4
Internal link audit

In Screaming Frog (JS-rendered crawl), go to the "JavaScript" tab — this shows links discovered only after JS execution. Review each: is this a navigation link that should be in static HTML? Is it in a component used across many pages? If yes, fixing this one component fixes thousands of pages.

Also check: does the site use router.push() or onClick for primary navigation? Search the codebase for these patterns.

Step 5
Core Web Vitals audit
  • PageSpeed Insights (pagespeed.web.dev) — lab + CrUX field data per URL
  • GSC → Core Web Vitals report — field data segmented by Good/Needs Improvement/Poor per URL group
  • Lighthouse (Chrome DevTools) — lab data + specific recommendations

Key checks: LCP — what is the largest element? Is it an image? Is it loaded eagerly with priority? CLS — open DevTools → Performance → record a page load → look for "Layout Shift" events. INP — look for long JS tasks on the main thread blocking interaction.

Step 6
Log file analysis

Filter for Googlebot user-agent. Segment by file type: HTML vs JS vs CSS vs images. If JS/CSS files represent >50% of Googlebot's requests, you have a crawl budget issue. Check for 5xx errors — Google throttles heavily after repeated 500s.

GSC approximation (no raw logs needed): GSC → Settings → Crawl Stats → By file type.

Step 7
Structured data validation
  • Google Rich Results Test (search.google.com/test/rich-results) — renders the page (executes JS) and validates schema
  • Schema.org Validator (validator.schema.org) — does NOT render JS — validates only what's in static HTML

Compare both outputs: if the Rich Results Test finds schema but the Schema.org Validator doesn't, your schema is JS-injected and at risk.

Step 8
Hreflang audit (multilingual sites)
  1. View Source → search for hreflang
  2. Verify all tags are absolute URLs (must include https://domain.com/)
  3. Verify correct ISO codes (e.g., en-GB not en-gb; uk ≠ United Kingdom)
  4. Verify x-default is present
  5. Verify reciprocity: if page A links to page B via hreflang, page B must link back to page A
  6. For Nuxt @nuxtjs/i18n: View Source specifically for encoded characters (%2F) in href attributes

Migration Playbook — Moving to a JS Framework Without Losing Rankings

Before the migration

Step 1
Full pre-migration crawl

Crawl the existing site with Screaming Frog. Export all indexed URLs (or import from GSC → Sitemaps). This is your baseline — every URL that's currently indexed needs to be accounted for after launch.

Step 2
Traffic mapping

Identify which URLs drive the most traffic via GSC or analytics. These are your highest-risk pages — they need extra attention and manual QA before launch.

Step 3
Redirect map

Map every legacy URL to its new URL. Every. Single. One. A 301 redirect that's missing after launch means that URL's link equity and ranking history are lost. No exceptions.

Step 4
Staging environment isolation

The most common post-launch disaster is forgetting to remove noindex from the staging environment. Check both:

  • <meta name="robots" content="noindex"> in HTML
  • X-Robots-Tag: noindex in HTTP response headers
  • Both CMS settings AND the frontend rendering layer — they can contradict each other

During the migration

Step 5
Match rendering mode or improve it

If the legacy site was server-rendered, the new framework must be at least SSR. Migrating to a pure CSR SPA is a guaranteed traffic loss. This is the single most common migration failure mode.

Step 6
Preserve URL structure

Identical URL = no redirect needed. If URLs must change, the redirect map from step 3 is non-negotiable. Changing URLs without redirects is equivalent to deleting your pages from Google's perspective.

Step 7
Rebuild metadata templates

Don't assume metadata migrates automatically. For every page template, verify that title, description, canonical, OG tags, and schema are correctly generated on the new framework. Test on staging before launch.

At launch

Step 8
Monitor GSC crawl stats immediately

A spike in 404s or 5xx errors within hours of launch is an emergency. Have the redirect map ready to deploy hotfixes. Check hourly for the first 24 hours.

Step 9
Submit updated sitemap + fetch critical pages

Submit the updated sitemap to GSC immediately after launch. Use GSC → URL Inspection → "Request Indexing" for the homepage, your top product/category pages, and a sample blog post.

Step 10
Monitor Core Web Vitals

The new framework may have different performance characteristics. Watch CWV for regressions in the first 2–4 weeks — the CrUX data will reflect the new site after enough traffic accumulates (usually 28 days).

Post-launch (90-day monitoring)

  • Weekly: indexed page count (GSC → Coverage), organic traffic (GSC → Performance), 404 rate
  • At 4 weeks: CWV field data updated in CrUX — check for regressions
  • Log file analysis: Confirm Googlebot is crawling HTML pages, not spending budget on JS files
  • Rankings: spot-check top 50 target keywords weekly

The AI Crawler Dimension

In 2025–2026, a new class of crawlers matters for SEO: AI agents that build the knowledge bases behind tools like ChatGPT, Perplexity, Claude, Gemini, and Bing Copilot.

CrawlerFetches HTMLDownloads JS filesExecutes JS

AppleBot✓✓✓ Full rendering
Bingbot✓✓Limited — Microsoft recommends SSR

Social unfurlers (Twitter, LinkedIn, FB)✓✗✗ No execution
Key Finding — Vercel/MERJ 2024

A CSR SPA is completely invisible to AI crawlers. Your content doesn't exist in their knowledge base. In an era where AI search surfaces (Perplexity, ChatGPT Search, Gemini) are increasingly used for discovery, being absent from those indexes is an emerging competitive disadvantage. SSR is no longer just an SEO best practice — it's the minimum viable architecture for visibility across the entire search ecosystem.

Optimising for AI crawlers

If you want visibility: serve clean, well-structured HTML. Use semantic elements (<article>, <section>, <h1>–<h6>). Implement JSON-LD schema. Eliminate JS dependencies for content. AI crawlers parse HTML the same way SEO-era crawlers did — semantic structure is everything.

Blocking AI crawlers (optional)

If you want to prevent AI crawlers from indexing your content (competitive or copyright reasons):

// app/robots.ts
export default function robots() {
  return {
    rules: [
      { userAgent: '*', allow: '/' },
      { userAgent: ['GPTBot', 'ClaudeBot', 'PerplexityBot', 'CCBot'], disallow: '/' },
    ],
  }
}
