01

The Core Problem

Traditional websites deliver HTML files verbatim. What the server sends is what the browser — and the crawler — sees. Simple, predictable, immediately readable.

JavaScript frameworks broke that contract. When a site is built as a pure Single Page Application (SPA), the server sends this:

HTML — What a CSR SPA actually sends
<!doctype html>
<html>
  <head><title>App</title></head>
  <body>
    <div id="root"></div>
    <script src="/static/js/main.bundle.js"></script>
  </body>
</html>

There is no content. The browser downloads the JS bundle, executes it, fetches data from APIs, builds the DOM in memory, and finally injects visible content into #root. Until that chain completes, the page is a blank shell.

Why this breaks SEO — at multiple levels

  • Crawlers that don't execute JS see nothing
  • Even Googlebot, which does execute JS, puts these pages in a rendering queue — introducing delays from seconds to weeks
  • Social-media unfurlers (Twitter, LinkedIn, Facebook) don't run JS — every page shows the same default preview
  • AI crawlers (GPTBot, ClaudeBot, PerplexityBot) fetch JS files but do not execute them — your content is invisible to them
Analogy

A static HTML site is like a printed menu on a restaurant table — anyone can read it immediately. A JS-only SPA is a menu that only appears after you scan a QR code, wait for an app to load, log in, and grant location permissions. Most impatient guests (crawlers) give up.

Why developers still use frameworks

Speed of development, rich interactivity, component reuse, shared logic between web and mobile. The problem isn't the frameworks themselves — it's deploying them in Client-Side Rendering mode for content that needs to be indexed. Meta-frameworks (Next.js, Nuxt, SvelteKit, Astro) exist precisely to solve this.

02

How the Browser and Googlebot Actually Read a Page

What HTML, CSS, and JavaScript each do

HTML
Declarative structure. Defines what exists — headings, paragraphs, links, images. This is what crawlers fundamentally rely on. Strong semantic HTML (<h1>–<h6>, <article>, <nav>, <main>) directly improves crawlability and LLM comprehension.
CSS
Presentation. Doesn't affect crawling but does affect Core Web Vitals — specifically CLS if fonts load without size reservations, and LCP if critical styles are blocked.
JavaScript
Behaviour and dynamism. Manipulates the DOM after the fact. This is what introduces complexity for crawlers — especially when it's the only way to produce content.
JS + CSR
When JS is the only source of content (no SSR), crawlers that don't execute JS see nothing at all. This is the worst possible configuration for SEO.

How a browser parses a page

  • Receives the raw HTML from the server
  • Parses it top-to-bottom, building the DOM tree
  • When it encounters <link rel="stylesheet">, it fetches CSS and builds the CSSOM
  • When it encounters a <script> without defer or async, it stops parsing until the JS downloads and executes (render-blocking)
  • Combines DOM + CSSOM into the Render Tree
  • Layout phase: computes positions and sizes
  • Paint phase: draws pixels on screen
Related — DOM article

The DOM tree, CSSOM, Render Tree, and how JS manipulates them are covered in detail in Le DOM & le rendu JS. Reading both articles together gives you the full picture of how Googlebot processes a modern page from raw bytes to indexed content.

How Googlebot processes a page — 3-stage pipeline

URL discovered → Crawl (fetch raw HTML) → Render Queue → WRS Render → Index
Stage 1 — Crawl
Googlebot fetches the raw HTTP response. Reads whatever HTML is in that response immediately. Any links in the static HTML are discovered now — no rendering needed.
Stage 2 — Render Queue
If JS is needed to reveal content, the URL goes into a queue. This queue is resource-constrained — pages can wait from seconds to weeks depending on the site's authority and crawl budget.
Stage 3 — WRS Render
Google's Web Rendering Service uses a headless Chromium instance (evergreen since May 2019). It executes JavaScript, fetches API data, builds the full DOM, and extracts content and links.

Critical constraints of the WRS

  • Stateless — no cookies, no localStorage, no session state persists between pages
  • Does not interact with the page (no clicks, no scroll, no form submission, no cookie-banner dismissal)
  • Has a 2 MB resource budget per page — heavy bundles may not fully execute
  • Has a ~5-second rendering timeout on average — queuing can extend total delay significantly
  • Content revealed only through user interaction (click, hover, scroll) is invisible
2024 Study Finding — Vercel / MERJ

Analysis of 100,000+ Googlebot fetches found that Google now renders virtually all pages returning a 200 status, including complex SPAs. However: server-rendered pages have an advantage because they skip the render queue entirely for content discovery.

Deep dive — DOM article

For WRS pipeline internals, the 2 MB truncation limit (March 2026), DOM vs HTML source discrepancies, and hydration mismatch diagnostics — see Le DOM & le rendu JS (15 sections, covers soft navigations, edge cases, and signal conflicts).

Rendering Modes — The Decision That Changes Everything

The rendering mode determines what content is in the HTML when a crawler first receives it — which determines everything else.

ModeWhat Googlebot sees on 1st fetchIndexed whenBest forSEO
CSREmpty <div id="root">Only after render queueAuthenticated dashboards, no-SEO appsAvoid
SSRComplete HTML with all contentImmediately on 1st crawlDynamic, frequently-changing contentExcellent
SSGPerfect static HTML, best TTFBImmediatelyBlog posts, docs, marketing pagesExcellent
ISRCached static HTMLImmediately (stale-while-revalidate)Large catalogues, pricing, inventoryExcellent
Streaming SSRCritical content in first chunkImmediatelyPages with slow data fetchingExcellent
Islands (Astro)Full static HTML, zero JS defaultImmediatelyContent-heavy sitesBest-in-class

Hybrid rendering — per-route strategy

Modern meta-frameworks let you choose rendering mode per route. A single Next.js codebase can:

  • SSG the /blog/* routes (static articles)
  • ISR the /products/* routes (catalogue updated daily)
  • SSR the /search route (real-time results)
  • CSR the /dashboard/* routes (authenticated, no SEO needed)

This is the architecture you want for most professional sites.

ISR — Incremental Static Regeneration (Next.js)

  • Pages start as SSG, then auto-rebuilt at a specified interval (revalidate: 300 = every 5 min) or on-demand
  • First request gets the cached page. In the background, Next.js rebuilds a fresh version. Next visitor gets the fresh version
  • Watch out for: brief windows where ISR page shows stale data (e.g., stock status mismatch)

Streaming SSR (Next.js App Router + React Suspense)

Instead of waiting for the entire page before sending HTML, the server streams HTML in chunks as components finish rendering. The browser receives the header and navigation immediately, then main content streams in.

SEO implication: The critical content (heading, body, metadata) is in the first chunk and arrives immediately — even on slow data-fetching pages, Googlebot sees the key content fast.

04

Next.js Deep Dive

Pages Router vs. App Router

Pages Router (original)
  • Files in /pages/ become routes
  • getStaticProps → SSG
  • getServerSideProps → SSR
  • Metadata via next/head
  • Well-documented, mature ecosystem
App Router (Next.js 13+, default since 14)
  • Files in /app/, route = folder with page.tsx
  • Server Components by default
  • New Metadata API (guaranteed in HTML)
  • Streaming SSR with React Suspense
  • Better SEO defaults, steeper learning curve
Audit note

For SEO work, identify which router the site uses — the audit approach differs significantly. Signal: <div id="__next"> + <script id="__NEXT_DATA__"> = Pages Router. self.__next_f.push( in source = App Router.

React Server Components (RSC) — Why They Matter for SEO

In the App Router, every component is a Server Component by default. Server Components render exclusively on the server, never ship their JS to the browser, and their content is always in the initial HTML — no rendering queue issue.

Common mistake

Wrapping entire page components in "use client" just to use one interactive element. This pushes all content into the client bundle, breaking SSR for that page. Fix: keep the page as a Server Component and isolate the interactive widget into a small Client Component.

The Metadata API — Critical for SEO

TypeScript — App Router (guaranteed in HTML) Recommended
// Dynamic metadata — runs on server before page renders
export async function generateMetadata({ params }) {
  const product = await fetchProduct(params.slug)
  return {
    title: `${product.name} | Your Store`,
    description: product.description,
    openGraph: {
      title: product.name,
      images: [product.coverImage],
    },
    alternates: {
      canonical: `https://example.com/products/${product.slug}`,
    },
  }
}
TypeScript — Title template (avoid repetitive suffixes)
// In root layout (app/layout.tsx)
export const metadata = {
  title: {
    template: '%s | Your Brand',
    default:  'Your Brand',
  },
}

// In any child page
export const metadata = {
  title: 'Product Name', // renders as "Product Name | Your Brand"
}
TypeScript — metadataBase (prevents staging domain leaks)
// In your root layout
export const metadata = {
  metadataBase: new URL('https://example.com'),
}
// Without this, relative URLs in metadata are left as-is.
// With it, /products/slug → https://example.com/products/slug

Structured Data (JSON-LD) — Correct vs broken pattern

Correct — Server Component
// app/products/[slug]/page.tsx
export default async function ProductPage({ params }) {
  const product = await fetchProduct(params.slug)
  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'Product',
    name: product.name,
    offers: {
      '@type': 'Offer',
      price: product.price,
    },
  }
  return (
    <>
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{
          __html: JSON.stringify(jsonLd)
            .replace(/</g, '\\u003c'),
        }}
      />
    </>
  )
}
Broken — useEffect injection
// Only fires after hydration
// Social crawlers and AI bots
// never see this schema

useEffect(() => {
  const script = document.createElement('script')
  script.type = 'application/ld+json'
  script.text = JSON.stringify(jsonLd)
  document.head.appendChild(script)
}, [])

next/image, next/font, next/link — Core Web Vitals impact

ComponentProblem it solvesKey usage
next/imageImage-related CLS, unoptimised formats, no lazy loadingAlways set width + height. Add priority to LCP image.
next/fontFont-swap CLS (self-hosts, uses size-adjust)Inter({ subsets: ['latin'], display: 'swap' }) in root layout.
next/linkJS-only navigation that crawlers can't followAlways use <Link href="..."> never <div onClick> for navigation.
Prefetch trap

On pages with hundreds of links (mega-menus, large catalogues), viewport-based prefetching fires dozens of background requests — exhausting server resources. Fix: <Link href="/..." prefetch={false}> on dense link clusters.

Framework-specific notes

Nuxt 3

  • SSR on by default with the Nitro server engine — portable to Node.js, Cloudflare Workers, Deno
  • useSeoMeta provides a typed, flat API for all metadata tags
  • routeRules allows per-route rendering: { '/blog/**': { prerender: true }, '/product/**': { isr: 3600 } }
  • @nuxtjs/i18n handles hreflang — but has known bugs (see Section 6.8 and Case Study 12)

SvelteKit

  • Svelte is a compiler, not a runtime — components compile to vanilla JS at build time, no Virtual DOM overhead
  • Typical SvelteKit page ships 30–50% less JS than an equivalent Next.js page
  • Per-page control via export const prerender = true and export const ssr = false
SvelteKit — Critical warning

adapter-static with ssr: false (SPA mode) is explicitly flagged as harmful to SEO in the SvelteKit official docs. This is a common misconfiguration that destroys crawlability.

Qwik

  • Eliminates hydration entirely via "resumability" — the server serialises full application state into the HTML
  • JS only downloads on-demand as the user actually interacts with specific elements
  • Near-instant TTI regardless of application complexity
  • Still a smaller ecosystem — less production case study evidence than Next.js

The Full Map of JS SEO Failure Modes

6.1 — JS-Only Internal Links: The Invisible Architecture Problem

The most common and most devastating JS SEO mistake. Navigation implemented with onClick handlers, router.push(), or <button> elements instead of <a href>.

Why it matters: Googlebot does not click buttons. The crawl graph is built from <a href> discovery. If your main navigation, category links, and product links are inside JS event handlers, Googlebot sees your site as a flat collection of orphan pages.

Invisible to crawlers
<div onClick={() => navigate('/shoes')}>
  Shoes
</div>

<button onClick={() => router.push('/shoes')}>
  Shoes
</button>
Crawlable
<Link href="/category/shoes">
  Shoes
</Link>

<a href="/category/shoes">
  Shoes
</a>

Screaming Frog check: Run a crawl with JS rendering disabled ("Text Only" mode). Any link that disappears compared to a JS-enabled crawl is a JS-only link.

6.2 — Content Not in Initial HTML

  • Symptom: View Source shows empty <div>. URL Inspection in GSC shows content, but indexing is delayed or unreliable
  • Cause 1: Pure CSR — the entire page relies on client JS
  • Cause 2: SSR set up incorrectly — getServerSideProps not actually fetching data before render
  • Cause 3: Content inside useEffect — runs only after hydration, never in SSR
  • Test: Open the page, then Ctrl+U (View Source). If your content isn't there, it's not in the initial HTML

6.3 — JS-Managed Metadata

  • What goes wrong: <title>, <meta name="description">, canonical tags, OG tags written by JS after page load
  • Consequence: Social-media previews use the static HTML (generic default). AI crawlers never see it
  • Fix (App Router): Use the Metadata API (generateMetadata). Tags are guaranteed in the initial HTML
  • Fix (Pages Router): Use next/head inside getServerSideProps — not inside useEffect

6.4 — Soft 404s from Hydration Failures

Soft 404: server returns HTTP 200, but Google decides the page has no content and removes it from the index.

  • Server renders correct HTML → JS bundle reaches browser → error during hydration → React error boundary unmounts the DOM → Googlebot sees blank screen → classifies as Soft 404
  • Detection: GSC → Coverage → "Soft 404" tab. Cross-reference with Sentry/Datadog for hydration-phase exceptions
  • Fix: Implement proper error handling. Use notFound() in Next.js App Router when data isn't found
Related — DOM article

The mechanics behind hydration mismatches — root causes (date APIs, browser-only APIs, invalid HTML structure), how React's error boundary destroys the DOM, and console-based diagnostics — are documented in Le DOM & le rendu JS — Section 06: Hydration mismatches.

6.5 — Crawl Budget Drain from Heavy JS

  • Rendering JS costs vastly more crawl resources than parsing static HTML
  • What gets wasted: rendering 500 KB JS bundles, following prefetch requests from next/link, crawling faceted navigation URLs
  • The signal: GSC → Settings → Crawl Stats → by file type. If 70–80% of Googlebot's requests are .js files, you have a budget problem

6.6 — Faceted Navigation & Index Bloat

E-commerce JS sites frequently generate millions of indexable URLs from filter combinations: /shoes?color=black&size=42&brand=nike&sort=price_asc

  • Keep low-value filter combinations client-only (update UI state without changing the URL)
  • For combinations that do get URLs, add <link rel="canonical"> pointing to the base category
  • Add robots.txt disallow for complex parameter strings

6.7 — Interaction Traps: Content Hidden Behind JS

Google does not interact with pages. Content behind a click, hover, scroll trigger, or "Load More" is invisible.

  • Tabs: render all tab content in HTML, use CSS to hide inactive tabs — not display: none via JS
  • Accordions: render all answers in HTML; use CSS to hide collapsed state
  • Infinite scroll: include a standard ?page=2 pagination link with a real href

6.8 — Hreflang Failures in JS Frameworks

Nuxt i18n bug #2764

Canonical and hreflang URLs are URL-encoded — slashes become %2F. Google sees https://example.com/fr%2Fproducts instead of the real URL. Entire hreflang implementation non-functional. Detection: View Source → search for %2F in hreflang href attributes.

6.9 — Hash Routing (React Router HashRouter)

  • All URLs look like example.com/#/products/slug
  • Everything after # is never sent to the server — and Google treats all hash URLs as the same page
  • Fix: Switch from HashRouter to BrowserRouter + server-side catch-all routing

Auditing a JS Framework Site — Step-by-Step Playbook

Step 1
Identify the framework and rendering mode
Signal in sourceFramework
<div id="__next"> + <script id="__NEXT_DATA__">Next.js (Pages Router)
self.__next_f.push( in sourceNext.js (App Router)
<div id="__nuxt"> + window.__NUXT__Nuxt
astro-island elements in DOMAstro
<sveltekit-data>SvelteKit
ng-version attribute on root elementAngular
Determine rendering mode: View Source (Ctrl+U) — is content in the raw HTML? Yes = SSR/SSG. No = CSR or broken SSR. Check HTTP headers: x-powered-by: Next.js, x-vercel-cache: HIT (ISR/SSG cache hit).
Step 2
Compare raw HTML vs rendered DOM — the core audit step
Run two crawls in Screaming Frog: (1) "Text Only" mode — JS disabled, what crawlers see on first pass. (2) "JavaScript" mode — what Googlebot sees after rendering.
  • Links in crawl 2 but absent in crawl 1 → JS-only links — critical problem
  • Metadata in crawl 2 but absent in crawl 1 → JS-managed metadata — at risk
Also use: GSC → URL Inspection → "Test Live URL" → "View Crawled Page". The HTML tab shows what Google's WRS saw. Screenshot tab shows what the page looked like visually to Google.
Step 3
Verify metadata in raw HTML
For every critical page template, View Source and search for — all must be present in raw HTML:
  • <title>
  • <meta name="description"
  • <link rel="canonical"
  • <meta property="og:title"
  • <script type="application/ld+json"
If any are absent or show generic/default values, that template has a metadata problem.
Step 4
Internal link audit
In Screaming Frog (JS-rendered crawl), go to the "JavaScript" tab — shows links discovered only after JS execution. Review each: is this a navigation link that should be in static HTML? Is it in a component used across many pages? Fixing one component fixes thousands of pages.
Step 5
Core Web Vitals audit
  • PageSpeed Insights (pagespeed.web.dev) — lab + CrUX field data per URL
  • GSC → Core Web Vitals report — field data segmented by Good/Needs Improvement/Poor per URL group
  • Lighthouse (Chrome DevTools) — lab data + specific recommendations
Key checks: LCP — what is the largest element? Is it an image with priority? CLS — DevTools → Performance → record page load → look for "Layout Shift" events. INP — look for long JS tasks on main thread.
Step 6
Log file analysis
Filter for Googlebot user-agent. Segment by file type. If JS/CSS files represent >50% of Googlebot's requests, you have a crawl budget issue. Check for 5xx errors — Google throttles heavily after repeated 500s. GSC approximation: GSC → Settings → Crawl Stats → By file type.
Step 7
Structured data validation
  • Google Rich Results Test (search.google.com/test/rich-results) — renders the page (executes JS) and validates schema
  • Schema.org Validator (validator.schema.org) — does NOT render JS — validates only static HTML
Compare both outputs: if Rich Results Test finds schema but Schema.org Validator doesn't, your schema is JS-injected and at risk.
Step 8
Hreflang audit (multilingual sites)
  • View Source → search for hreflang
  • Verify all tags are absolute URLs (must include https://domain.com/)
  • Verify correct ISO codes (en-GB not en-gb; uk ≠ United Kingdom)
  • Verify x-default is present
  • Verify reciprocity: if page A links to page B via hreflang, page B must link back
  • For Nuxt @nuxtjs/i18n: View Source specifically for encoded characters (%2F) in href attributes

Migration Playbook — Moving to a JS Framework Without Losing Rankings

Before the migration

Step 1
Full pre-migration crawl
Crawl the existing site with Screaming Frog. Export all indexed URLs (or import from GSC → Sitemaps). This is your baseline — every URL that's currently indexed needs to be accounted for after launch.
Step 2
Traffic mapping
Identify which URLs drive the most traffic via GSC or analytics. These are your highest-risk pages — they need extra attention and manual QA before launch.
Step 3
Redirect map
Map every legacy URL to its new URL. Every. Single. One. A 301 redirect that's missing after launch means that URL's link equity and ranking history are lost. No exceptions.
Step 4
Staging environment isolation
The most common post-launch disaster: forgetting to remove noindex from the staging environment. Check both:
  • <meta name="robots" content="noindex"> in HTML
  • X-Robots-Tag: noindex in HTTP response headers
  • Both CMS settings AND the frontend rendering layer — they can contradict each other

During the migration

Step 5
Match rendering mode or improve it
If the legacy site was server-rendered, the new framework must be at least SSR. Migrating to a pure CSR SPA is a guaranteed traffic loss. This is the single most common migration failure mode.
Step 6
Preserve URL structure
Identical URL = no redirect needed. If URLs must change, the redirect map from step 3 is non-negotiable. Changing URLs without redirects is equivalent to deleting your pages from Google's perspective.
Step 7
Rebuild metadata templates
Don't assume metadata migrates automatically. For every page template, verify that title, description, canonical, OG tags, and schema are correctly generated on the new framework. Test on staging before launch.

At launch & post-launch (90-day monitoring)

Launch day
Monitor GSC crawl stats hourly for first 24h. Spike in 404s or 5xx errors = emergency. Submit updated sitemap immediately. Request indexing for homepage + top pages via GSC.
Week 1–4
Weekly: indexed page count (GSC → Coverage), organic traffic (GSC → Performance), 404 rate. At 4 weeks: CWV field data updated in CrUX — check for regressions.
Month 2–3
Log file analysis: confirm Googlebot is crawling HTML pages, not spending budget on JS files. Spot-check top 50 target keywords weekly.
Ongoing
Rankings: spot-check top 50 target keywords monthly. CWV: set up Real User Monitoring (RUM) for continuous INP/CLS/LCP tracking in production.

The AI Crawler Dimension

In 2025–2026, a new class of crawlers matters for SEO: AI agents that build the knowledge bases behind ChatGPT, Perplexity, Claude, Gemini, and Bing Copilot.

Key finding — Vercel/MERJ 2024

A CSR SPA is completely invisible to AI crawlers. Your content doesn't exist in their knowledge base. In an era where AI search surfaces are increasingly used for discovery, being absent from those indexes is an emerging competitive disadvantage. SSR is no longer just an SEO best practice — it's the minimum viable architecture for visibility across the entire search ecosystem.

Optimising for AI crawlers

  • Serve clean, well-structured HTML — semantic elements (<article>, <section>, <h1>–<h6>)
  • Implement JSON-LD schema in the initial HTML (not JS-injected)
  • Eliminate JS dependencies for content — AI crawlers parse HTML the same way SEO-era crawlers did

Blocking AI crawlers (optional)

TypeScript — app/robots.ts
export default function robots() {
  return {
    rules: [
      { userAgent: '*', allow: '/' },
      { userAgent: ['GPTBot', 'ClaudeBot', 'PerplexityBot', 'CCBot'], disallow: '/' },
    ],
  }
}
