01

TL;DR & Seuils clés

Le rapport Crawl Stats (Paramètres → Statistiques d'exploration) est l'outil le plus proche d'une analyse de logs serveurs accessible gratuitement à tous les propriétaires de propriétés "domaine". Il révèle ce que Googlebot fait réellement sur votre site sur 90 jours via 3 KPIs principaux et 4 répartitions. Il est jugé "advanced users" par Google et indispensable au-delà de ~1 000 URLs.

Response time idéal
≤ 100ms
Alarme à 500 ms. Throttling Googlebot probable à 1 000 ms (John Mueller).
Ratio Refresh / Discovery
80 / 20
Régime stationnaire attendu. Toute déviation forte raconte une histoire.
Réponses 200 OK
≥ 80%
Les 3xx, 4xx, 5xx doivent rester marginaux et stables.
Signaux 5xx critiques
< 1%
2-3 jours consécutifs de 5xx = réduction long-terme du crawl (Mueller).
📌 Pattern à connaître

Hausse soudaine simultanée de "Total requests" + chute du response time + hausse du download size = nouvelles pages massivement publiées. Hausse des requests avec hausse du response time + 5xx = surcharge serveur.

⚠ Idée reçue

Bloquer des URLs en robots.txt n'augmente pas automatiquement le crawl budget des autres pages — sauf si votre serveur était précédemment en saturation. Les deux seuls leviers réels : (1) ajouter des ressources serveur, (2) améliorer la qualité du contenu (popularité, valeur utilisateur, unicité). Clarification officielle Google, déc. 2025.

02

Anatomie du rapport Crawl Stats

Le rapport est accessible uniquement aux propriétés root-level (Domain property ou URL-prefix à la racine), via Paramètres → Exploration → Statistiques d'exploration → Ouvrir le rapport. Il agrège 90 jours de données échantillonnées sur l'activité de Googlebot.

❌ Différences vs logs serveur

Les données Crawl Stats diffèrent des logs sur deux points : (1) les requêtes envisagées mais non exécutées (ex. robots.txt indisponible) sont comptées dans le total — d'où les écarts possibles avec vos logs. (2) Chaque maillon d'une chaîne de redirection est compté séparément : page1 → 301 → page2 → 301 → page3 = 3 requêtes.

Quand utiliser Crawl Stats
Dès ~1 000 URLs indexables. Essentiel post-migration, après un lancement de section, lors d'une stagnation d'indexation ou d'un drop de trafic inexpliqué.
Quand aller plus loin
Au-delà de ~100 k URLs ou face à une anomalie inexpliquée : compléter avec une vraie analyse de logs (Screaming Frog Log Analyser, JetOctopus, Botify).
Host Status — section méconnue
Trois sous-statuts sur 90 jours : robots.txt fetch (doit être 0 % d'échec), DNS resolution (proche de 0 %), server connectivity. Pour Domain properties : top 20 des hosts enfants avec statut par host.
Bots usurpés (spoofed)
Crawl Stats peut compter des bots malveillants usurpant Googlebot. Cas Glenn Gabe : 90 % des "Googlebot" étaient des bots spoofés. Toujours croiser logs + reverse DNS.
03

Les 3 KPIs principaux

KPI 1 — Total crawl requests

Définition Google : le nombre total de requêtes d'exploration émises pour des URLs de votre site, qu'elles aient abouti ou non. Analogie : c'est le "trafic Googlebot" — plus un site est jugé important, plus le postier passe souvent.

Pattern observéInterprétation probableAction
Hausse régulière sur plusieurs semainesGoogle augmente sa Crawl capacity : votre site est plus rapide / plus de contenus frais / plus de signaux de qualitéVérifier que la hausse profite aux pages stratégiques, pas aux paramètres
Pic isolé puis retour à la normaleMigration, redesign, lancement massif, ouverture d'une section bloquée, ou AdsBot (Dynamic Search Ads)Vérifier l'onglet "Par type de Googlebot" pour identifier la source
Plateau / stagnation en publiantCrawl budget plafonné — perceived value insuffisanteAméliorer le maillage interne, soumettre un sitemap propre, retirer les pages thin
Chute brutaleHostload exceeded, robots.txt qui 5xx, baisse de qualité perçue, core updateVérifier Host status, server logs, recent core update
Ratio crawls/jour vs pages > 10xCrawl waste typique : Googlebot tourne sur des paramètres / facetsAudit faceted navigation, robots.txt, canonicals
✓ Cas concret — CDN sous-domaine

En déplaçant images, JS, CSS sur un sous-domaine cdn.example.com, Search Engine Journal a augmenté le crawl rate des pages HTML principales — l'écosystème "main domain" récupère le budget précédemment consommé par les ressources statiques.

💡 Cas e-commerce — LinkGraph 2026

Site 85 000 produits : indexation des nouveaux produits qui prenait 3-4 semaines, perte estimée à ~50 k$/mois. Diagnostic : 45 % du crawl budget gaspillé sur des facets (?color=, ?sort=). Solution : robots.txt + canonicals self-referencing → ratio de gaspillage tombé à 12 %, +125 k$/mois en revenu organique sous 90 jours.

KPI 2 — Total download size (bytes)

Définition Google : nombre total d'octets téléchargés depuis votre site pendant l'exploration. Si Total requests est le nombre de visites du postier, le download size est le poids cumulé du courrier qu'il emporte. À nombre de visites égal, plus c'est lourd, moins Googlebot peut crawler dans le temps imparti.

Ce qui fait monter le download size
  • Templates plus lourds post-refonte
  • Sites JS : dual fetch HTML + WRS
  • XHR/POST supplémentaires (cas JetOctopus : 62 % du crawl sur AJAX non rentable)
  • PDF, vidéos non bloqués
  • Scripts tiers en cascade
  • DOM massif généré dynamiquement
Comment réduire le download size
  • Ressources statiques sur CDN/sous-domaine séparé
  • Compression images (WebP, AVIF), minification CSS/JS
  • Bloquer ressources non critiques au rendu (avec précaution)
  • Prerendering / SSR pour sites JS lourds
  • lastmod W3C correct : jusqu'à -22 % de recrawl inutile (JetOctopus)

KPI 3 — Average response time (ms)

Proxy du TTFB (Time To First Byte) vu par Googlebot. Ce n'est pas le temps de chargement utilisateur, ni un signal Core Web Vitals. C'est ce que Googlebot mesure entre sa requête et le premier octet renvoyé.

ValeurStatutSource
≤ 100 msExcellentJohn Mueller (Lumar Office Hours) — cible recommandée
100–200 msBonSeuil utilisé par Google dans PageSpeed Server Response Time
200–500 msÀ surveillerPas critique mais piste d'optimisation
500–1 000 msProblématiqueGooglebot peut commencer à throttler
≥ 1 000 msCritiqueMueller : "Googlebot won't be able to crawl as much as it ideally would"
⚠ Impact sur le crawl — à retenir

Si un sous-dossier de votre site (ex. /blog/) ralentit, Google peut réduire le crawl rate de tout le host, y compris vos pages produit performantes. Couplé à des 5xx, Mueller rappelle que 2-3 jours consécutifs suffisent pour déclencher une réduction long terme du crawl.

Diagnostiquer et corriger le response time

Étape 1 — "By file type"
Seuls les HTML lents → problème backend / DB. Images lentes → problème CDN. JS/CSS lents → bundling ou serveur statique.
Étape 2 — Host status
DNS / robots.txt / server connectivity. Coche verte = ok. Point d'exclamation = à investiguer immédiatement.
Étape 3 — TTFB utilisateur
Croiser avec PageSpeed Insights, WebPageTest, Chrome DevTools Network pour confirmer côté utilisateur.
Étape 4 — Fixes serveur
Cache page (Varnish, Cloudflare Cache Reserve), cache objet (Redis), optimisation DB. CDN avec edge caching. HTTP/2 ou HTTP/3, Brotli.

3. By Purpose — Discovery vs. Refresh

La répartition la plus stratégique. John Mueller (Search Central live, nov. 2020) : "Refresh crawling is when we update information we already have. Discovery crawling is when we find new URLs we've heard about — through new internal links or backlinks."

Ratio Refresh / DiscoveryInterprétationQuand c'est anormal
80 / 20Régime stationnaire sain (Edward Bate, Servebolt, JC Chouinard)—
95 / 5Site stable, peu de nouveau contenu, ou maillage interne faibleSi vous publiez régulièrement : sitemap obsolète, pages orphelines
50 / 50 ou Discovery > RefreshMigration en cours, lancement, gros import, ou crawl trap (facets)Vérifier d'urgence si le pic Discovery porte sur des URLs voulues ou parasites
70 / 30 stableSite en croissance régulièreSain pour un éditeur publiant souvent
📌 Symbiose avec Index Coverage

Si beaucoup d'URLs en "Discovered – currently not indexed" mais peu de Discovery dans Crawl Stats → Google a vu le lien mais décidé de ne pas crawler (signal qualité ou serveur). Si Discovery est élevé mais l'indexation n'avance pas → problème de qualité de contenu, pas de crawl.

05

Outils avancés GSC

Au-delà du Crawl Stats, les vraies puissances avancées de GSC permettent de démultiplier la granularité d'analyse et d'automatiser les audits à grande échelle.

Performance & Search Analytics
  • Filtres RegEx RE2 (max 4 096 chars)
  • Comparaison de périodes + segmentation device / pays
  • Connecteur Looker Studio (modèles Aleyda Solis)
  • API Search Analytics (~25 k lignes/requête)
  • Bulk Data Export → BigQuery (sans limite 1 000 lignes)
URL Inspection API
  • 2 000 URL/jour/propriété, 600/min
  • Données : lastCrawlTime, googleCanonical, robots.txt state
  • Hack pro : vérifier plusieurs propriétés (sous-dossiers) → quota multiplié
  • Natif dans Screaming Frog (Config → API Access)
  • Détection canonicals ignorés par Google
Index Coverage — nuances
  • Limite UI : 1 000 lignes par catégorie
  • Hack Glenn Gabe : sous-dossiers comme propriétés séparées
  • "Crawled – not indexed" → signal qualité (thin, duplication)
  • "Discovered – not indexed" → boost via maillage interne + sitemap
  • "Soft 404" → fréquent e-commerce (produits épuisés)
Core Web Vitals
  • Source CrUX (field data, 28 jours roulants, 75e percentile)
  • LCP ≤ 2,5 s — INP ≤ 200 ms — CLS ≤ 0,1
  • Statut groupe = pire des 3 métriques
  • Compléments : PageSpeed Insights, web.dev, Chrome DevTools
  • Distinct du response time Googlebot (TTFB crawl ≠ ranking)

RegEx avancés dans Performance

Cas d'usagePattern RE2
Brand vs. non-brand(?i)mybrand|misspellings → filter "Doesn't match"
Questions (informational)^(who|what|when|where|why|how|does|can|is|are|did|should|could)\b
Long-tail (6+ mots)\b(\w+\s+){5,}\w+\b
Striking distancePosition > 10.9 + filtre URL /blog/ + RegEx questions
⚠ Syntaxe RE2

RE2 ne supporte pas les lookbehind / lookahead / backreferences. Tester vos patterns sur regex101.com en flavor "Golang" avant de les utiliser dans GSC.

📌 Bulk Data Export → BigQuery

Toutes les performances, pas de limite à 1 000 lignes, pas d'échantillonnage majeur, conservation au-delà de 16 mois. Indispensable pour les analyses long-terme, les jointures avec GA4 sur l'URL, et les requêtes SQL custom (ex. impressions par cluster sémantique). Coût BigQuery très bas : free tier suffisant pour la plupart des sites < 100 k pages indexées. Partition expiration recommandée à 12–16 mois.

06

Use cases par type de site

E-commerce (10 k–1 M URLs)
  • Risque #1 : faceted navigation → URLs explosives
  • Surveiller : ratio HTML vs. paramètre, % d'URLs avec 3+ facets crawlées
  • robots.txt strict sur les combinaisons inutiles (price+sort)
  • Canonicals self-referencing, rel="nofollow" sur liens facet non rentables
  • KPI cible : > 70 % du crawl HTML sur pages indexables + StoreBot présent
Éditorial / Média (publication quotidienne)
  • Risque #1 : Discovery faible si maillage interne pauvre
  • Surveiller : Discovery > 15 %, Smartphone bot dominant
  • Sitemap "news" séparé, hubs sujets bien maillés, lastmod W3C exact
  • Pings via IndexNow (Bing) + "Request Indexing" pour les articles phares
  • KPI cible : Refresh ~80 %, response time < 200 ms même pendant pics
PBN / Niche site (< 1 000 pages)
  • Crawl Stats non obligatoire sous 1 000 pages — mais utile
  • Détecter un host qui ne réveille pas Googlebot (spam / pénalité)
  • Vérifier après publication si Discovery a eu lieu sous 24 h
  • KPI cible : 100 % réponses 200, response time < 300 ms
SaaS / B2B
  • Risque : sections authentifiées qui consomment du crawl
  • Cas Stackmatix : 12 % du crawl gaspillé sur app/ non indexable
  • robots.txt strict sur app/, dashboard/, account/, etc.
  • Surveiller le dual-fetch WRS sur les pages JS-heavy
07

Monitoring mensuel & Caveats

Méthodologie de monitoring

  • Hebdo Crawl Stats overview — pic de requests, response time, host status. Tout pic anormal → investigation immédiate.
  • Hebdo Pages report — nouveau "Crawled – not indexed", nouveau "Discovered – not indexed" ; valider les fixes en cours.
  • Mensuel Performance — RegEx brand/non-brand, striking distance, comparaison MoM/YoY. Identifier les opportunités page 1.
  • Mensuel Core Web Vitals — % URLs Good vs. Poor, suivi des templates en alerte. Prioriser les templates à fort trafic.
  • Trimestriel Analyse de logs serveur si > 100 k URLs — cross-check avec Crawl Stats pour valider les anomalies.
  • Annuel / Post-migration Setup BigQuery, URL Inspection bulk, full crawl Screaming Frog/Sitebulb. Audit complet de l'architecture de crawl.

10 caveats à connaître

⚠ Caveat 1 — Crawl Stats est échantillonné

Le rapport montre la majorité des requêtes mais pas toutes. Sur des incidents critiques (perte massive de trafic, migration), ne jamais se fier uniquement à GSC — corroborer avec logs et un crawl tiers.

⚠ Caveat 2 — Limite de 1 000 lignes

La plupart des UI exports (Index Coverage, Crawl Stats par catégorie) sont limités à 1 000 lignes. Workarounds : vérifier sous-dossiers comme propriétés séparées (Glenn Gabe), URL Inspection API, Bulk Data Export, ou logs.

⚠ Caveat 3 — Lag de données

Les données Crawl Stats peuvent traîner de plusieurs jours (jusqu'à une semaine). Pour les changements en temps réel, utiliser logs ou outils tiers (Cloudflare analytics, monitoring uptime).

❌ Caveat 4 — Bugs Index Coverage

Le report Index Coverage a connu des bugs (déc. 2025 : freeze depuis mi-novembre, signalé par Glenn Gabe et Jan Caerels). Toujours vérifier la cohérence des dates affichées avant toute analyse.

📌 Caveat 5 — Response time ≠ signal ranking direct

L'Average response time mesuré par Googlebot ne pèse pas directement dans le ranking. Mais il pèse sur le crawl → l'indexation → le ranking. Mueller : "unlikely to be used in rankings, unless consistently problematic 5-10+ seconds."

📌 Caveat 6 — Discovery vs. Refresh sont approximatifs

Mueller lui-même : "I'm not 100% sure what exactly we would put into each of those buckets." Ne pas en faire une science exacte ; les grandes tendances suffisent.

📌 Caveat 7 — AI Overviews / AI Mode (avril 2026)

Le tracking des clics AIO dans GSC est anonymisé selon les expériences récentes de JC Chouinard — les clics sont attribués à la position de l'AI Overview, sans détail de la position interne. Limite à connaître pour le reporting.
